# 用户中心参考设计

参考项目：`D:\GitHub\dadi\dadi-user-center`。本文件提炼其用户中心的边界，作为 Harness 工程的身份和授权设计依据，不复制 Java/Spring 实现。

## 参考项目采用的模型

`dadi` 把平台和租户分开：一个平台可以有多个租户，租户是业务数据隔离边界。用户记录带有 `platform_id` 和 `tenant_id`，用户名在租户范围内唯一。用户状态包括待激活、启用、锁定和禁用。

用户中心还保存：

- 组织树：组织可有父子关系。
- 岗位：岗位属于租户并可挂到组织。
- 用户组织关系：用户可属于多个组织，并可标记主组织和岗位。
- 用户组和组成员：用于复用授权关系。
- 平台、租户和审计事件。
- 用户会话、登录事件和凭据摘要。

认证使用服务端管理的 OIDC/OAuth2 流程。浏览器只收到 HttpOnly 会话标识，访问令牌和 PKCE 校验信息留在后端。登录请求中的平台、租户、客户端和回调地址由服务端的白名单注册表解析，浏览器不能自行指定这些安全参数。

请求进入业务接口前，服务端从认证身份和已验证的 Host/租户选择解析平台租户上下文。上下文不一致时拒绝请求；不同租户的浏览器会话不能继续当前授权流程。跨服务调用通过受信的内部身份解析或网关传递用户、租户和角色上下文，服务端不能把普通请求头当作可信身份来源。

参考项目的安全特点是 fail closed：未知平台、未知租户、重复租户选择、客户端与租户不匹配、回调地址未注册、身份上下文不一致，都会拒绝或重新登录，而不是猜测默认值。

## 适配到 Harness 工程

当前 Harness 工程建议采用三层身份模型：

```text
Platform
  └── Tenant
        ├── User
        ├── Organization / Post
        ├── Group / GroupMember
        └── AgentSession / Run / Artifact
```

`platform_id` 用于区分平台实例和平台级管理员；`tenant_id` 是 Agent 会话、任务、工作区、产物、配额和审计的隔离边界；`user_id` 是具体操作人。普通请求必须同时携带服务端生成的 `platform_id`、`tenant_id`、`user_id` 和角色集合。

当前 `mysql-schema.md` 中的 `tenant_memberships` 应按参考项目调整为“租户内用户主记录 + 可选跨租户授权关系”：默认用户属于一个租户，跨租户访问必须显式建立授权关系并经过管理员审批。这样可以避免把“用户能登录”误认为“用户能访问所有租户”。

Harness 侧不实现密码、OIDC Provider 或 token 签发。建议通过用户中心 OIDC 登录，Harness API 只验证签发方、issuer、audience、签名、过期时间和租户声明，再向用户中心或内部目录查询最新角色和状态。用户被禁用、租户被暂停或成员关系撤销后，新的任务必须被拒绝；长任务由能力令牌和租约机制限制，不只依赖初始 JWT 的有效期。

## 对当前 schema 的具体调整

在 `users`、`tenants`、`sessions`、`runs`、`audit_events` 之外增加或明确：

- `platforms`：平台实例、代码、状态和域名。
- `organizations`：租户内的组织树。
- `posts`：租户内岗位。
- `user_organizations`：用户、组织和岗位关系。
- `groups`、`group_members`：租户内用户组关系。
- `oauth_clients`：客户端归属的平台、租户、允许的回调地址和 scope。
- `user_sessions`：服务端会话状态、过期时间和撤销时间；只存哈希或加密后的服务端数据。
- `login_events`：登录成功、失败、锁定和拒绝记录。

所有租户内表都带 `platform_id` 和 `tenant_id`。跨表关系优先使用包含这两个字段的复合外键，避免把租户 A 的用户关联到租户 B 的组织。管理端跨租户查询使用独立的平台管理员接口，不能复用普通租户仓储。

## 采用参考项目时保留的边界

参考项目的 Java/Spring、Vue、数据库迁移文件和内部 header 名称不直接搬入 Python 工程。Harness 只复用其身份模型、服务端会话方式、平台/租户绑定、OIDC 客户端白名单、fail-closed 规则和审计原则。
