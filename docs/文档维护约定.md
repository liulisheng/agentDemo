# 文档维护约定

## 文件命名

项目级 `docs/` 文件使用中文文件名，例如：

```text
架构总览.md
数字员工数据模型.md
接口与状态流程.md
前端交互设计.md
```

OpenSpec 固定 artifact 文件名保持英文，以保证 CLI 能够识别。

## 每个代码变更必须同步文档

新增或修改以下内容时，必须更新对应中文文档：

| 代码变化 | 文档要求 |
|---|---|
| 新增模块 | 更新目录说明和架构图 |
| 修改领域对象 | 更新数据模型图和字段说明 |
| 修改 API | 更新接口和时序图 |
| 修改状态 | 更新状态图和异常流程 |
| 修改前端路由 | 更新页面地图和交互说明 |
| 修改 Runtime | 更新引擎边界、能力和恢复流程 |
| 修改部署 | 更新部署拓扑、配置和回滚步骤 |

## 文档内容要求

每份设计文档应包含：

- 状态
- 更新时间
- 适用范围
- 目标、功能边界、使用角色和租户/权限约束
- 架构图或流程图
- 主流程、异常/超时/取消/重试等相关流程或时序图
- 数据表/数据模型、字段说明、关系、约束、索引、迁移和回滚
- API 契约或状态说明，包括错误类别、幂等和异步行为
- 安全与凭据边界、审计/Trace/Usage 记录
- 已验证行为
- 未验证项
- 依赖和限制
- 关联代码目录
- 验证命令

## HTML 原型要求

- 每个新增或改变用户行为的功能都要提供独立 HTML 原型，统一放在 `docs/原型/<功能名>.html`，并在 OpenSpec design 与项目设计文档中链接。
- 功能设计、流程、数据模型/表结构、API/状态、权限、安全和验收说明必须另行形成 Markdown 文档；HTML 原型保持为独立 `.html` 文件，不用 HTML 代替 Markdown 文档，也不把完整原型嵌进 Markdown。
- 原型使用自包含 HTML/CSS/JavaScript 和明确标注的演示数据；不得连接真实后端、触发真实模型调用或包含 API Key、SecretRef 对应的密钥值。
- 原型至少展示主流程、关键操作、租户范围、权限可用/拒绝、空/加载/错误和操作结果状态。模型/连接功能还应展示凭据未配置、连接失败、目录为空、模型测试成功/失败等状态。
- 后台功能用管理或运维状态页作为原型；窄屏、键盘焦点和基本可访问性也需考虑。
- HTML 原型是方案交付物，实施时需要同步更新，不能用静态截图或纯文字线框替代。

## 完成标准

代码任务只有同时满足以下条件才能勾选完成：

1. 代码实现完成。
2. 自动化测试和检查通过。
3. HTML 原型与实际交互保持一致。
4. 中文文档、图示、已验证/未验证项、限制说明和验证命令已更新。

## SQL Schema 和 Migration

- 可执行 MySQL schema/migration SQL 的唯一目录为 `docs/migrations/`；部署脚本和说明引用该目录，不复制第二份 SQL。
- 每个新建或变更的表必须填写中文表级 `COMMENT`；每个新建或变更的字段必须填写中文字段级 `COMMENT`，准确说明业务含义。
- 已应用 migration 保持不可变。历史表或字段需要补充说明时，使用新的 forward migration 更新数据库 COMMENT，不修改已发布 SQL 文件。
- MySQL 集成验证必须查询 `information_schema.TABLES` 与 `information_schema.COLUMNS`，确认本次迁移新增或变更的表、字段均有中文注释。
- 对应 OpenSpec design/tasks 必须写明 migration 文件、中文 COMMENT 要求和校验方式。

## 提交和代码说明

- Commit message、commit body 和 Pull Request 描述必须使用中文。
- Commit body 必须说明变更内容、影响范围、验证结果、风险和后续计划。
- 公共类、函数、端口、适配器、Worker 和 API 路由必须有中文注释或文档字符串。
- 状态转换、租户边界、Runtime 边界、重试和错误处理必须补充中文原因说明。
- 提交前排除密钥、虚拟环境、缓存和本机 Agent 配置。
